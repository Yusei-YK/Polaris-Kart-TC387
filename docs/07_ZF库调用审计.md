# code/user 与逐飞 TC387 库调用审计

审计日期：2026-07-13。范围为 `Kart_TC387/code/`、`Kart_TC387/user/`、工程 `.cproject` 以及同工程内 `Kart_TC387/libraries/` 的逐飞声明和实现。

## 结论

- `Kart_TC387/code/` 目前只有说明文本，没有 C/H 源码；实际业务代码全部位于 `Kart_TC387/user/`。
- 当前已接入的电机、编码器、转向绝对值编码器、IMU、SBUS、VOFA 串口、IPS200 和 5ms PIT 都真实调用了仓库内逐飞 TC387 API，函数名、参数顺序和枚举类型已逐项对照。
- `kart_calc`、`kart_pid`、`kart_light`、`kart_mission` 不直接调用逐飞函数是正常分层：它们是纯算法/策略层，硬件访问由下层封装完成。
- 不能据此宣称全车可比赛：灯板扫描底层、实体菜单按键、前轮角度环、yaw 外环、路径规划/记录/回放、语音和蜂鸣器仍未完成。

## 为什么转向编码器没有直接调用 `absolute_encoder_init`

逐飞 `zf_device_absolute_encoder` 的协议与当前传感器相同，但该库版本把设备引脚硬编码成 SPI0 的 P20.11/P20.14/P20.12、CS=P20.13；本车 IMU963RA 正在使用这组 SPI0 引脚。当前转向传感器实际接在 SPI4 的 P22.3/P22.0/P22.1、CS=P23.1。

因此直接调用逐飞设备层会造成总线和 IMU 冲突。当前 `kart_steer_abs` 保留板级协议适配，但所有总线操作仍使用逐飞 `spi_*`、`gpio_*` 和延时函数。这是必要适配，不是绕开逐飞底层。初始化现在会返回自检结果，失败后不再更新伪造角度。

## 本次修正

- 处理 `imu963ra_init()` 返回值；失败时不再继续做 1.5s 零偏标定或启动姿态更新。
- IMU 换算改用逐飞 `imu963ra_gyro_transition` / `imu963ra_acc_transition`，避免量程变化后写死系数失效。
- 修复姿态 reset 只改内部四元数、没有同步输出四元数的问题。
- 转向绝对编码器增加初始化自检状态；失败时停止更新角度，并在 IPS200 实时页显示 IMU/ABS 状态。
- IMU、IPS200 的板级审阅宏改为直接引用逐飞驱动宏，避免两份配置表漂移。
- 明确灯板为 UART0，并把 TX/RX 改成逐飞 `UART0_TX_P14_0` / `UART0_RX_P14_1` 枚举；同时标出 Debug UART 冲突。
- 给速度参数、编码器读数、遥控快照和 PWM 请求增加中断临界区，避免主循环与 5ms/UART 中断读写到半更新状态。
- `kart_control_set_enable(0)` 立即清零上一拍后轮请求，且主循环改为先处理调参命令再 `power_sync()`。
- `isr.c` 显式包含 `board_pins.h`，确保 5ms 宏有定义。

## 仍需 ADS/实物确认

- 当前机器没有 TASKING/ADS 编译器，不能完成 TC387 全工程链接；主机端测试不能替代 ADS 编译。
- PWM 正负方向宏、左右编码器 sign、绝对编码器中心/软限、IMU 坐标方向都必须按实车验证。
- `e0` 软件清零路径已修并有主机测试，但此前“电机不停”的硬件现象必须重新悬空复测后才能关闭安全项。
- 当前 UI 只有事件接口，没有实体按键/旋钮逐飞驱动；灯板也只有图案逻辑，没有 TLD7002 通信和扫描。
