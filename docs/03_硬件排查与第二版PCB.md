## 致命问题：转向绝对编码器 MOSI/CS 错位

### 结论

第一版和第二版 PCB 都把转向角传感器的 MOSI 布到了 `P23.1`，但 `P23.1` 不是 TC387 合法 SPI4 MOSI 引脚。转向绝对编码器需要 MOSI 写配置寄存器，MOSI 不通会导致自检失败或读数异常。

当前代码期望接线：

```c
#define KART_STEER_ABS_SPI_INDEX        (SPI_4)
#define KART_STEER_ABS_SPI_SCK_PIN      (SPI4_SCLK_P22_3)
#define KART_STEER_ABS_SPI_MOSI_PIN     (SPI4_MOSI_P22_0)
#define KART_STEER_ABS_SPI_MISO_PIN     (SPI4_MISO_P22_1)
#define KART_STEER_ABS_SPI_HW_CS_PIN    (SPI_CS_NULL)
#define KART_STEER_ABS_CS_GPIO_PIN      (P23_1)
```

### 证据链

- 模块线序：1=GND，2=VCC，3=SCLK，4=MISO，5=MOSI，6=CS。
- 2x3 排针是反序映射。
- 反序后实际落点：

| 模块信号 | 实际 MCU | 当前代码 | 结果 |
|---|---|---|---|
| SCLK | P22.3 | P22.3 | 一致 |
| MISO | P22.1 | P22.1 | 一致 |
| MOSI | P23.1 | P22.0 | 错 |
| CS | P22.0 | P23.1 | 错 |

### 处理

- 第一版：已飞线，把模块 MOSI 引到 `P22.0`，CS 引到 `P23.1`，**v1 转向绝对编码器已实测通过**。
- 第二版：定版前交换转向角传感器座子 `.1/.2` 焊盘（免飞线）。
- 备选：改软件 SPI 兜底，但硬件修正优先。

## 已解决：三路编码器 v1 全通(2026-07-07 更新)

**旧结论作废**：此前记录"右后编码器 TIM5 读数恒 0""转向绝对编码器待飞线"。经 v1 实测：

- 左后编码器 `P33.7/P33.6`、TIM2 正常。
- 右后编码器 `P10.3/P10.1`、TIM5 正常出数。
- 转向绝对编码器 SPI4（飞线后）正常读 raw。

三路编码器反馈在 v1 上均已打通，不再是待查项。保留下述 TIM5 与 TIM2 模式差异笔记，供后续低速方向抖调试参考：

- `kart_encoder.c` 左右读取逻辑对称。
- TC387 库中 TIM5 与 TIM2 模式不同：TIM2 是真正交解码，TIM5 更像计数 + 方向电平判断，低速方向可能抖。

## 安全硬件缺口

当前第一阶段没有补齐以下硬件能力：

- 后轮驱动 EN/nSLEEP。
- 后轮驱动 nFAULT。
- 三路电流采样。
- 独立硬件急停。

风险：

- 只有软件写 PWM=0，不等于硬件级关断。
- 堵转、短路、过温时软件可能无感知。
- 程序跑飞时软件急停可能失效。

当前取舍：用户已知第一阶段先靠软件限幅、短时测试和断电兜底。后续第二版仍建议补齐 EN/nSLEEP、nFAULT、电流采样和硬件急停。

## 当前事故与待查

- 转向上电打死导致单驱芯片烧穿，断电后转向电机电流倒灌回主板，炸主板电源 Q1（30V/90A P-MOS）和 D1（BZT52C16 栅极钳位），并击穿单驱 U15（SN74HC125）。根因与整改已查清，详见交接主文档第 1、2 节。
- **【最高级安全隐患】开机后未发任何指令，后轮自动转；reset 后继续转；只有重新编译烧录才停（队友摸到核心板很烫直接断电，未进一步验证）。**
  - 关键推断：reflash 能停、reset 不停 → 说明普通复位没能清掉驱动后轮的那个"源"，只有烧录时长时间 halt 内核 + 完整复位序列才切断。
  - **【已推翻的错误假设，留档警示】** 曾怀疑是"速度环失能→`kart_remote_poll` 遥控默认接管后轮"（`cpu0_main.c:50-53` + `kart_power.c:296-299`）。**但用户明确：上电时 UART3 压根没接遥控接收机，遥控器至今从未成功控制过电机。** 无接收机 → UART3 收不到帧 → `kart_remote_timeout_ticks` 恒 0 → `kart_remote.online` 恒 0 → `kart_remote_poll` 只会走 else 分支写 **0**。遥控接管这条路走不通，该假设作废。
  - **软件侧复核结论（已排除软件命令自转）**：cpu1/2/3 全空（仅 `disable_Watchdog`+空循环），只有 cpu0 驱动电机；全工程写 PWM/DIR 的点都在 `kart_power.c`，无隐藏第二写入源。开机后每一拍软件对后轮的输出全是 0（`power_init` 清零；`power_check_poll` 因 `KART_POWER_BOOT_CHECK_ENABLE=0` 不写 duty；速度环失能分支写 0；remote 离线写 0；`power_sync` 把 0 刷进 PWM）。**结论：在"无接收机+速度环默认失能"下，软件没有命令后轮转。**
  - **根因重新指向硬件/复位瞬态（待通电验证，勿臆断）**：
    1. 被炸驱动板的 MOS/栅极驱动处于半导通或闩锁态，PWM=0 也挡不住（反灌那次已伤过它）。
    2. DRV8701 使能/输入脚在 MCU 复位瞬间被拉到导通电平：复位时 MCU 引脚高阻，若驱动板输入无下拉可能浮到导通；且 `kart_set_dir_pwm` 在 duty=0 时仍 `gpio_high(dir_pin)`，DIR 常拉高配合损坏驱动行为不可预期。
  - **一步定位实验**：开机后量 MCU 三路 PWM 输出脚（在串联电阻**之前**、直接量 MCU 引脚）。恒 0 → 问题 100% 在驱动板/功率级；有非零波形 → 回到 MCU/GTM 复位态配置再查 `pwm_init`。
  - **核心板发烫是独立第二警报**：正常跑 PWM 发热应在驱动板 MOS，不该烧核心板。核心板烫提示反灌能量可能又进主板（主板整改未做，反灌路仍敞开），或 MCU IO 被反向注入导致内部钳位二极管持续导通（latch-up 前兆）。**主板三项整改是"电机能安全转起来"的前置条件，不是以后再说。**
  - 叠加缺陷（与自转不同源，但通电前应一并加固）：失能只在内存写 0，真正 PWM=0 全靠主循环 `power_sync()`(`cpu0_main.c:55`)，主循环被 `system_delay_ms`/阻塞式 VOFA 拖住时 PWM 保持上一非零值；`Power_now`/`kart_speed` 无 volatile、无临界区，5ms 中断与主循环并发有竞态；无硬件级急停兜底。
- `e0` 关闭速度环后电机停不住：结论待定。软件层失能确实命令 duty=0，若仍停不住需按上面"硬件/复位瞬态"方向查，并注意 DRV8701 在 duty=0 时可能为滑行(coast)而非制动。
- 双驱左后轮疑似烧毁：平均速度 I1 卡在 19~22，符合"左轮 0、右轮单独约 40、平均约 20"的假象，待单路验证。

### 通电前安全操作（自转事故后新增，不可省）

1. 后轮离地架空 + 电机先拔线，只给逻辑供电；动力电用限流电源，不要直接上电池。
2. 开机时发射器关机或拨到非 armed 档、油门归中；先验证"关掉遥控，后轮是否还自转"，直接区分是遥控接管还是别的源。
3. 复现时盯 VOFA ch4(RX 字节)，观察是否有遥控帧被 latch。

### 待批的软件加固方案（纯软件，编译即可验证）

1. 开机默认不接管：`kart_remote_poll` 要求"先收到合法遥控帧 + 拨杆显式 0→2 上升沿"才允许接管，禁止开机即接管，禁止油门非中位直接冲。
2. 失能兜底进中断：5ms 中断失能分支直接 `pwm_set_duty(...,0)`，不等主循环刷。
3. 共享量加 `volatile` + 成组写入关中断保护，消除竞态。
4. (可选)软件看门狗：一定周期无有效"允许运行"信号就强制 PWM=0。
